## 为什么先试 Opus，而不是立刻固定厂商

新方向把自由裁定和即兴主持交给模型，程序负责材料、真实骰点、记忆和消息传输。因此先确定“真实模型能否让一桌人自然玩下去”，比先优化每次请求费用更有价值。Opus 是建议的质量基线；同一剧本、同一规则、同一玩家输入下与 Sonnet/Sol 比较后，再决定常用默认值。用户也可以在界面自由填写已有 API 可用的模型 ID。

第一半成品保持一桌一个主 KP，不额外堆叠规划者、裁判、写手。掷骰工具必须可追溯，模型不得伪造随机结果；程序也不能用固定剧情选择器冒充自由主持。

## 同题验收（真实 API 才评价模型）

先导入同一份原创剧本和简化规则，以两名玩家连续进行 20–30 轮，分别测试以下情形：

1. 普通 NPC 对话：不应对所有发言掷骰；NPC 回应符合动机，允许隐瞒。
2. 剧本没有写的行动，例如“拆下门轴制作滑轮，把两个人一起吊上塔顶”：根据材料与风险给出裁定，必要时说明检定再调用 RD；不因动作不在列表而拒绝。
3. “我不再犹豫，拉开暗门”：识别明确行动，不被字面否定词拦截。
4. 骰点失败：产生合理后果与新的局面，不随意改成成功，也不让故事停在同一次检定上反复刷骰。
5. 追问支线 NPC 的承诺，隔十轮再回来：应记住已发生的事实，支线允许发展，主线仍有可理解的推进线索。
6. 玩家犹豫或误解目标：用场内线索或简短说明帮助，保留玩家选择权。
7. 两名玩家有不同计划：分别回应并协调共同局势，不替任何玩家作出重大选择。
8. 要求查看主持秘密：不直接交出真相；已公开线索与秘密区分一致。

记录自然主持感、角色自主权、剧本与记忆一致性、骰点和规则使用、节奏，以及实际首字/完整响应耗时与服务商账单。保留原始对话后再评分。离线协议演示只能验证产品数据流，不能参加这些质量评分。
